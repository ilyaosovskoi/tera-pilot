## Bugs found and fixed during this batch

1. **Stale server leaked the API token (P0.3 regression instance).** The
   Tera Pilot process that was running at the start of the session was
   started from pre-P0.3 code: `GET /api/status` returned `api_token`, and
   the HTTP confirmation routes (`/api/action/respond`,
   `/api/guardian/respond`) did not exist (headless confirmations failed
   **open**). Restarting on the current working tree closed both: the token
   is no longer present in `/api/status`, and it is only delivered through
   the same-origin HTML page (`window.__TERA_PILOT_TOKEN`). Verified live
   after restart. **No code change was needed** — the running process was
   simply stale.

2. **LM Studio 400 `Invalid diff` kills agent runs (engine bug, worked
   around in Tera Pilot).** When the model generated a native tool call
   whose `content` contained quotes (e.g. `query = f"SELECT * FROM users
   WHERE username = '{username}'"`), LM Studio's engine rejected its own
   generated tool call with `400 … "Invalid diff: '…' not found at start of
   '…'"` (server_error 500 inside) — at **generation** time, before Tera
   Pilot ever saw a response. Reproduced with plain `chat/completions`
   requests (every tool name, stream on/off), so it is an LM Studio / LFM
   2.5 engine bug, not a Tera Pilot bug. Fixed on the Tera Pilot side:
   - `runtime.py` never echoes the model's raw (possibly malformed)
     `tool_calls` arguments back into the conversation — each call is
     rebuilt from the parsed args dict (valid JSON).
   - the `Invalid diff` 400 is now treated as retryable, with a one-time
     corrective hint appended to the conversation.
   - **primary fix**: `LMStudioProvider.emits_native_tool_calls = False`
     → the runtime stops advertising the `tools` schema to LM Studio, so
     the engine never validates generated tool calls; the model's native
     text format `<|tool_call_start|>[name(arg='…')]<|tool_call_end|>` is
     parsed by a new LFM parser in `OutputParser`.

3. **LFM-native text parser (new).** `OutputParser` gained LFM-block
   extraction and Python-style argument parsing (named + positional args,
   `\'`/`\n` escapes, brace/paren-aware splitting), with positional args
   mapped to each tool's documented parameter order.

4. **Positional-arg mapping bug (found via `review-sql-injection`).** A
   mixed form `write_file(path='REVIEW.md', '<content>')` assigned the
   positional content to `path` (overwriting it). Fixed: positional values
   fill the first parameter slot not already taken by a named argument.
   Verified against the captured failing output — the call now parses as
   `path='REVIEW.md', content=<1092 chars>`.

All changes are covered by unit tests
(`tests/test_agent_runtime_quality.py`, `tests/test_eval_*.py`); the
relevant suites pass (35 + 66 tests green).

## Security observations

- **P0.3 token delivery**: verified fixed on the current server (token
  only via the served HTML page; `/api/status` no longer leaks it).
- **P0.4 fail-closed confirmations**: the new `/api/action/respond` and
  `/api/guardian/respond` routes exist; the eval driver now auto-answers
  them so headless runs do not stall (mirrors the browser "Allow" click).
- The `sec-*` adversarial tasks (SSRF, prompt injection, npm backdoor)
  were **not** run in this batch (skipped per request) — see below.

## Caveats

- Only 5 tasks, one run each, one model — this is a smoke batch, not a
  benchmark. The plan's "5–10 repeats per task" (P1.6) was not executed.
- The direct (no-Tera-Pilot) comparison driver was built and unit-tested
  but no direct runs were executed.
- Token/cost metrics are not meaningful this batch (usage tracker resets,
  local model = $0).
- `review-sql-injection` failed before the parser fix landed; it should be
  re-run to confirm the fix.
- Results include runs against a server that was restarted several times
  during debugging; iterations/durations are the observable evidence.
